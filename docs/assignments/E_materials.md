# 资料与展示同学负责：内容有依据、效果有记录、提交不漏项

**你要确认比赛到底交什么，准备可靠的校园内容，找同学真正用一遍，再把大家的成果整理成能提交的介绍、视频和支撑材料。**

这项工作不是最后补文档：场景价值20分、实施成效20分、文档展示15分都需要你的证据。开发者负责说明自己实际做成了什么，你负责核对、组织与整理；D协助画面和材料排版。

## 具体要做什么

1. 首先核对[比赛依据](../REQUIREMENTS.md)与飞书提交原文，确认入口、18日具体截止时刻、申报/承诺模板、签字要求和评审访问条件。当前飞书全文因登录未取得，只核实了本地PDF与提供截图；新增或冲突要求写明原文位置和更新时间，并马上交A。
2. 明确首批面向哪个校区、谁会用、解决哪几个真实问题。可先收集3–5条典型需求，数量是工作建议；给B/C具体输入例子，避免只写“大学生都需要陪伴”。不收集可识别个人的私密情绪日记。
3. 依据选定场景整理一小批可核查校园事实，建议先10–20条。每条写事实、校区、官方链接、核对日期和适用范围，填知识来源表交C；没有依据的精确时间、地点和电话不导入。地图/校园照片写来源和许可，交B/D。
4. 14–15日先写作品介绍与视频结构，事实性结果留空。16日拿A给的真实版本组织自愿试用，建议先3–5位非开发同学；实际人数按实报。每人依相同任务体验，记录匿名编号、日期、版本、完成/失败、耗时和原话反馈，把阻塞及时交对应开发者。
5. 统一统计口径：流程完成率写“完成完整规定流程人数/尝试人数”；等待时间从发送到首个可用答复，写实际次数和测量方式；重试、失败和缺失值单列。小样本只描述观察，不宣称证明心理疗效或全校效果。不把合成样例、开发者自测混作真实用户试点。
6. 收A的入口/版本/服务结果、B的真实截图和录屏、C的实际配置/提示词/知识库/工作流、D的资源说明。按[提交清单](../submission/CHECKLIST.md)整理PDF、MP4、效果图和支撑材料；“已完成”必须能找到证据，未完成写计划。
7. 17日按评审顺序彩排：链接能否打开、痛点和机制是否说清、关键流程是否真实、成效数字是否可追溯、附件是否同版本。18日帮助A核对并保存实际回执；签字身份材料只交授权提交入口，不放代码仓库。

## 你放哪里，怎么交接

知识放 `content/knowledge/`，校园素材放 `content/assets/campus/`，匿名试用放 `content/pilot/`，公开程度合适的材料草稿放 `docs/submission/`。分别已有来源表和记录模板。不会Git可以交同结构文件夹给A；更新[你的交接记录](../handoffs/E/current.md)，或请A代录。

| 时间 | 接收者 | 必须交付 |
| --- | --- | --- |
| 14日或最迟15日上午 | A及全员 | 赛务未决项、准确截止时刻（查到才填）、目标校区、典型问题 |
| 15日 | C、B/D | 首批有来源知识、校园图文及适用范围；材料结构 |
| 16日 | A/B/C | 真实试用记录、清楚的失败步骤、原话反馈与问题优先级 |
| 17日 | A | 同版本介绍/视频/截图/支撑包、成效统计依据、已检查与缺失事项 |
| 18日 | A | 最终附件核对结果和回执整理 |

## 怎样算完成

C能按来源复核事实；B/D能看懂素材适用地点；开发者能依试用步骤复现问题；介绍中的功能和数据都有出处。演示视频按现有通知为MP4、≤10分钟且≤500MB，支撑材料PDF/ZIP总≤100M；如最新通知改变，先记录依据再同步。最新全文尚未读到时不要勾为完成。

若16日还没有真实可用版本，立即把阻塞交A/C；先做文案结构与已验证部分，不能靠模拟视频补造实施成效。D可承担封面排版和图片整理，B/C分别提供可用录屏与配置说明，避免你最后独自补所有内容。
